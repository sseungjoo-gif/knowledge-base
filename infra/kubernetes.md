# 쿠버네티스 · 클라우드 인프라 — 실제 겪은 순서로 이해하기

> 개념을 나열하지 않고, **프로젝트에서 실제로 부딪힌 순서**대로 정리했습니다.
> "왜 이게 안 되지?"를 겪은 지점마다 필요한 개념이 나옵니다.

---

## 0. 전체 그림 — 무엇이 무엇을 담고 있나

가장 먼저 잡아야 할 것은 **포함 관계**입니다. 이게 헷갈리면 이후 모든 게 헷갈립니다.

```
VPC (네트워크 구획)
 └─ 서브넷 (용도별 IP 구간)
     └─ VM (서버 한 대)
         └─ [일부 VM이 모여] 쿠버네티스 클러스터
             └─ 네임스페이스 (논리 구획)
                 └─ Pod (컨테이너 묶음)
```

**핵심** — 클러스터도 결국 VM 위에 만들어집니다. 그리고 **같은 VPC 안에 있어도 클러스터에 속하지 않는 VM이 함께 존재**할 수 있습니다.

| 구분 | 무엇인가 | 예시 |
|---|---|---|
| VPC | 격리된 가상 네트워크 | `DEV VPC` |
| 서브넷 | VPC를 용도별로 쪼갠 IP 구간 | LB / Mgmt / Workload / DB |
| VM | 실제 서버 한 대 | 접속용 VM, 온톨로지 VM |
| 클러스터 | VM 여러 대를 묶은 논리 단위 | NKS 클러스터 |
| 노드 | 클러스터에 속한 VM | 워커 노드 6대 |
| 네임스페이스 | 클러스터 내부의 논리 구획 | `apex`, `kube-system` |
| Pod | 컨테이너가 실행되는 최소 단위 | 백엔드 Pod |

## 1. VPC와 서브넷 — 네트워크의 뼈대

### VPC (Virtual Private Cloud)

클라우드 안에 만드는 **격리된 가상 네트워크**입니다. 자체 IP 대역을 갖고, 그 안에 서버들이 들어갑니다.
물리 장비도 아니고 서버 한 대도 아닙니다. **여러 자원이 들어가는 공간**입니다.

> 보통 **환경 단위로 나눕니다** — 개발/스테이징/운영을 각각 별도 VPC로 두어 네트워크 자체를 격리합니다.

### 서브넷 (Subnet, 줄여서 S/N)

VPC를 용도별로 쪼갠 하위 네트워크입니다. 각각 IP 대역을 갖고 방화벽·라우팅을 따로 적용할 수 있습니다.

| 서브넷 | 역할 |
|---|---|
| **LB S/N** | 로드밸런서. 외부 트래픽을 받는 유일한 입구 |
| **Mgmt S/N** | 관리용. 운영자가 접속하는 서버(배스천/점프 서버) |
| **Workload S/N** | 실제 서비스가 도는 곳 |
| **DB S/N** | 데이터베이스 전용. 가장 안쪽 |

**왜 나누는가** — 보안 계층화입니다. 외부 → LB → Workload → DB 순으로 안쪽으로 갈수록 접근을 좁힙니다. **외부에서 DB로 직접 가는 경로를 아예 만들지 않는 것**이 목적입니다.

## 2. 클러스터와 네임스페이스 — 논리 구조

### 클러스터

VM 여러 대를 묶어 **하나의 자원 풀처럼 관리**하는 단위입니다. 쿠버네티스가 컨테이너를 어느 VM에 띄울지 알아서 배치합니다.

### 노드 그룹 (Node Pool)

같은 사양·용도의 노드 묶음입니다. 이름 뒤에 붙은 문자열은 **개별 노드 식별자**입니다.

```
skn-agent-p-ng-w-6710     ┐
skn-agent-p-ng-w-93da     │ 노드그룹 "skn-agent-p-ng-w" 의 노드 4대
skn-agent-p-ng-w-d2f3     │
skn-agent-p-ng-w-e27f     ┘
```

**여러 대로 두는 이유** — 가용성(1대 죽어도 다른 노드로 재배치), 부하 분산, 무중단 패치.

### 네임스페이스 (Namespace)

클러스터 **내부의 논리 구획**입니다. 권한·리소스 쿼터·네트워크 정책을 나누는 단위입니다.

> **중요** — 네임스페이스는 노드에 묶이지 않습니다.
> 하나의 네임스페이스의 Pod들이 **여러 노드에 분산 배치**됩니다.
> 특정 노드에 고정하려면 `nodeSelector`·`nodeAffinity`·`taint/toleration` 설정이 필요합니다.

### 오해하기 쉬운 지점

> **"apex가 e27f 노드에 있다"는 건 지금 이 순간의 상태일 뿐입니다.**
> Pod가 재시작되면 다른 노드로 옮겨갈 수 있습니다.

## 3. 클러스터 안인가 밖인가 — 가장 많이 헷갈리는 지점

같은 VPC 안이라도 **클러스터 소속 여부**에 따라 모든 것이 달라집니다.

| | 클러스터 소속 (노드) | 클러스터 밖 독립 VM |
|---|---|---|
| 배포 방식 | kubectl / GitOps | docker, 직접 설치 |
| 장애 대응 | 자동 재배치·복구 | 직접 관리 |
| 통신 방법 | **Service DNS로 호출** | **IP로 직접 호출 + 방화벽 필요** |
| 모니터링 | 클러스터 통합 | 별도 구성 |

### 판별 방법

```bash
kubectl get nodes -o wide
```

여기에 해당 VM의 호스트명이 **나오면 클러스터 노드**, 안 나오면 **클러스터 밖**입니다.

> 실무 팁 — VM 안에서 `systemctl status kubelet` 이 동작 중이면 클러스터 노드입니다.

## 4. 방화벽 — 왜 Pod에서 외부 VM으로 못 가는가

### ACG (Access Control Group)

네이버 클라우드의 **방화벽**입니다. AWS의 Security Group과 같은 역할입니다.

| 특성 | 내용 |
|---|---|
| 적용 단위 | **서버 단위** (네트워크 경계가 아님) |
| 방식 | **화이트리스트** — 허용한 것만 통과 |
| 상태 저장 | **Stateful** — 요청이 통과하면 응답은 자동으로 나감 |
| 기본값 | 인바운드 전체 차단 / 아웃바운드 전체 허용 |

**Stateful이라는 점이 중요합니다** — 받는 쪽의 **인바운드만 열면** 되고, 응답용 규칙을 따로 만들 필요가 없습니다.

### ★ 출발지 IP 함정 — 가장 많이 틀리는 부분

**Pod에서 클러스터 밖으로 나가는 트래픽의 출발지는 Pod IP가 아니라 노드 IP입니다.**

Pod IP는 클러스터 내부 전용 주소라, 밖으로 나갈 때 노드가 **자기 IP로 주소를 변환(SNAT)**해서 내보냅니다.

```
Pod (10.244.x.x)  →  노드 (10.192.60.x)  →  외부 VM (10.192.61.150)
                     ↑ 여기서 출발지가 바뀜
```

| 잘못된 설정 | 올바른 설정 |
|---|---|
| Pod IP 대역 등록 | **노드 IP 또는 노드 서브넷 대역** 등록 |

> Pod IP는 재기동마다 바뀌므로 방화벽 규칙으로 쓸 수 없습니다.
> 노드가 증설·교체되면 IP도 바뀌므로 **서브넷 CIDR로 등록**하는 것이 안전합니다.

### LB IP로 열면 안 되는 이유

**방향이 반대이기 때문입니다.**

| 방향 | 성격 | 등록할 값 |
|---|---|---|
| 외부 → 클러스터 | 인바운드, LB 경유 | LB IP가 **목적지** |
| 클러스터 → 외부 VM | 아웃바운드, **LB를 거치지 않음** | 노드 IP가 **출발지** |

## 5. 통신이 안 될 때 — 원인 찾는 순서

증상이 비슷해도 원인은 여러 층에 있습니다. **아래 순서로 좁히면 빠릅니다.**

### ① 받는 쪽에서 패킷이 오는지 확인

```bash
# 대상 VM에서 실행
sudo tcpdump -i any port 3000 -nn
```

그 상태에서 보내는 쪽에서 요청을 쏩니다.

```bash
# Pod에서
kubectl run nettest --rm -it --image=busybox:1.36 -n apex -- sh
nc -zv -w 5 10.192.61.150 3000
```

**판정**

| tcpdump 결과 | 원인 |
|---|---|
| 아무것도 안 찍힘 | **중간 차단** — ACG · Network ACL · 사내 방화벽 |
| SYN만 반복 | **받는 쪽 문제** — OS 방화벽 또는 서비스 미기동 |
| SYN → SYN-ACK → RST | **정상 연결** (`nc -z`는 확인 후 바로 끊음) |

> `Flags [R]`(RST)이 보인다고 실패가 아닙니다. **출발지가 누구인지**를 봐야 합니다.
> 요청한 쪽이 보낸 RST면 정상 종료, 받는 쪽이 보낸 RST면 거부입니다.

### ② 받는 쪽이 포트를 열고 있는지

```bash
ss -tulpn | grep 3000
```

| 결과 | 의미 |
|---|---|
| `0.0.0.0:3000` | 외부 접속 가능 ✅ |
| `127.0.0.1:3000` | **자기 자신에서만 접속 가능** ❌ |
| 아무것도 없음 | 서비스가 안 떠 있음 |

### ③ OS 방화벽 확인

```bash
sudo systemctl status firewalld
sudo iptables -L -n
```

### ④ 자기 자신에게 호출

```bash
curl -v --max-time 5 http://localhost:3000/
```

여기서도 안 되면 **방화벽 문제가 아니라 서비스 문제**입니다.

### ⑤ 다른 위치에서 대조

관리 서버(배스천)에서도 쏴봅니다.

| 결과 | 결론 |
|---|---|
| 관리서버는 되고 Pod만 안 됨 | **출발지 대역이 ACG에 누락** |
| 둘 다 안 됨 | ACG 규칙 자체 문제 또는 서비스 문제 |

### 흔한 실수 세 가지

1. 규칙을 **받는 쪽이 아니라 보내는 쪽** ACG에 등록
2. **Pod IP 대역**을 등록
3. 컨테이너 포트 매핑 누락 — `docker ps`의 PORTS에 `0.0.0.0:3000->3000` 이 보여야 함

## 6. Ingress — 도메인과 경로 라우팅

### Ingress

클러스터 외부에서 들어오는 HTTP 요청을 **도메인·경로 기준으로 내부 서비스에 연결**하는 규칙입니다.

### 같은 도메인에 여러 경로

**충돌이 아닙니다.** 오히려 FE와 BE가 같은 오리진이 되어 CORS 문제가 사라집니다.

```yaml
rules:
- host: example.company.co.kr
  http:
    paths:
    - path: /api          # 백엔드
      pathType: Prefix
    - path: /agent        # 기존 경로 — 명시적으로 보존
      pathType: Prefix
    - path: /             # 프론트엔드 (가장 마지막)
      pathType: Prefix
```

**주의할 점**

- 경로 매칭은 **더 구체적인 것이 우선**합니다
- `/`를 Prefix로 두면 **하위 경로를 전부 흡수**하므로, 기존 경로가 있다면 명시적으로 남겨야 합니다
- 같은 host를 여러 Ingress 리소스에 나눠 쓰면 **중복 정의 시 먼저 생성된 것이 이깁니다** → 한 리소스에 모으는 것이 안전

### 확인 명령

```bash
kubectl get ingress -A -o wide      # 전체 호스트·경로
kubectl describe ingress <name> -n <ns>
```

## 7. SSE — 실시간 전달이 안 될 때

### SSE (Server-Sent Events)

서버가 응답을 한 번에 주지 않고, **연결을 열어둔 채 여러 번 나눠 보내는 방식**입니다.

```
요청 ──▶
     ◀── "해석 완료"       (1초)
     ◀── "조회 중 40%"     (3초)
     ◀── "판정 완료"       (12초)
     ◀── 최종 결과 → 종료  (15초)
```

**용도** — 처리에 시간이 걸릴 때 진행 상황을 먼저 보여주기 위함입니다.

### ★ 버퍼링 함정

중간 장비가 응답을 모아서 한꺼번에 보내면, **이벤트가 실시간으로 오지 않고 마지막에 몰려서** 도착합니다. 그러면 SSE를 쓰는 의미가 없습니다.

**확인 방법**

```bash
curl -N http://<주소>/<엔드포인트>
```

이벤트가 **한 줄씩** 나오면 정상, 마지막에 몰려 나오면 버퍼링입니다.

**점검할 곳**

| 위치 | 설정 |
|---|---|
| Ingress (nginx) | `nginx.ingress.kubernetes.io/proxy-buffering: "off"` |
| Ingress 타임아웃 | `proxy-read-timeout` 연장 |
| 로드밸런서 | 유휴 연결 타임아웃 확인 |
| 대상 서버 앞단 nginx | 동일하게 버퍼링 해제 |

## 8. 자주 쓰는 명령 모음

### 현황 파악

```bash
kubectl config get-contexts                  # 현재 컨텍스트·네임스페이스
kubectl get namespaces                       # 네임스페이스 목록
kubectl get nodes -o wide --show-labels      # 노드 IP·라벨
kubectl get all -n <ns>                      # 네임스페이스 주요 자원
kubectl get pods -n <ns> -o wide             # Pod가 어느 노드에 있는지
```

### 전체 자원 조회

`get all`은 Ingress·ConfigMap·Secret·PVC를 포함하지 않습니다.

```bash
kubectl api-resources --verbs=list --namespaced -o name \
  | xargs -n1 kubectl get --show-kind --ignore-not-found -n <ns>
```

### 문제 추적

```bash
kubectl describe pod <pod> -n <ns>
kubectl logs <pod> -n <ns> --tail=100 -f
kubectl get events -n <ns> --sort-by=.lastTimestamp
kubectl auth can-i --list -n <ns>            # 내 권한 확인
```

### 편의 설정

```bash
kubectl config set-context --current --namespace=<ns>   # 기본 네임스페이스 변경
```

### VM에서 확인 (kubectl 없이)

```bash
hostnamectl                 # OS·커널·가상화
ip addr                     # 사설 IP (서브넷 판별)
ss -tulpn                   # 열린 포트
docker ps                   # 컨테이너 상태
systemctl status kubelet    # 클러스터 노드인지 판별
free -h / df -h             # 자원 현황
```

## 9. 배포 파이프라인 — Git · Nexus · Harbor

| 도구 | 담는 것 | 역할 |
|---|---|---|
| **Git** | 소스 코드 | 파이프라인의 시작점 |
| **Nexus** | 라이브러리·패키지 | 빌드 재료 저장소 + 외부 저장소 캐시 |
| **Harbor** | 컨테이너 이미지 | 완성품 저장소 |

```
Git push → CI 빌드 (Nexus에서 의존성) → 이미지 생성
→ Harbor push → 쿠버네티스가 Harbor에서 pull → 실행
```

**핵심 구분** — Nexus는 **빌드 재료**, Harbor는 **완성된 실행 이미지**입니다.

### 인바운드가 막힌 환경에서 벤더 이미지 받기

외부에서 사내 Harbor로 push할 수 없다면 **방향을 뒤집습니다.**

| 방식 | 내용 |
|---|---|
| **Pull Replication** (권장) | 벤더가 자기 레지스트리에 올리고, 사내 Harbor가 **아웃바운드로 당겨옴** |
| 오프라인 전달 | `docker save` → tar 전달 → `docker load` |
| 중계 레지스트리 | DMZ에 경계 레지스트리를 두고 2단 구성 |

**Pull Replication 설정 시 필요한 것**

- 원격 레지스트리를 **Registry Endpoint로 등록** (주소 + 읽기 계정)
- **Replication Rule** 생성 (대상 저장소·태그, 수동/주기 실행)
- **아웃바운드 방화벽 허용** (해당 도메인 443)

> 자동 주기 동기화는 벤더가 태그를 덮어쓸 때 운영 이미지가 바뀔 수 있으므로,
> **수동 실행 또는 특정 태그만 동기화**하는 편이 안전합니다.

### 함께 챙길 것

- **취약점 스캔 정책** — 벤더 이미지는 베이스가 오래되어 CVE가 다수 검출되는 경우가 흔함. 배포 직전에 막히지 않도록 사전 협의
- **프로젝트 분리** — 자체 개발 이미지와 벤더 이미지를 다른 프로젝트로 나눠 권한·정책을 따로 적용
- **버전 정합성** — 자체 배포와 벤더 릴리스의 호환 조합을 기록

## 부록. 용어 빠른 찾기

| 용어 | 한 줄 정의 |
|---|---|
| ACG | 서버 단위 방화벽 (네이버 클라우드) |
| CIDR | IP 대역 표기법 (`10.192.60.0/24`) |
| Ingress | 도메인·경로 기준 외부 트래픽 라우팅 규칙 |
| Namespace | 클러스터 내부 논리 구획 |
| Node | 클러스터에 속한 VM |
| Node Pool | 같은 사양·용도의 노드 묶음 |
| Pod | 컨테이너 실행 최소 단위 |
| Service DNS | 클러스터 내부에서 서비스를 이름으로 호출하는 주소 |
| SNAT | 나가는 트래픽의 출발지 주소를 바꾸는 것 |
| SSE | 연결을 유지한 채 서버가 여러 번 나눠 보내는 방식 |
| Stateful (방화벽) | 요청이 통과하면 응답은 자동 허용 |
| Subnet (S/N) | VPC를 용도별로 나눈 IP 구간 |
| Taint / Toleration | 특정 노드에 아무 Pod나 못 오게 하는 장치 |
| VPC | 클라우드 내 격리된 가상 네트워크 |
| nodeSelector | Pod를 특정 노드에 배치하는 설정 |

## 부록. 실무 체크리스트

**새 외부 연동을 붙일 때**

- [ ] 대상이 클러스터 안인가 밖인가 (`kubectl get nodes`)
- [ ] 밖이라면 ACG에 **노드 서브넷 대역**을 출발지로 등록
- [ ] 받는 쪽 서비스가 `0.0.0.0`에 바인딩되어 있는가
- [ ] 받는 쪽 OS 방화벽이 꺼져 있거나 허용되어 있는가
- [ ] `tcpdump`로 패킷 도달 여부 확인
- [ ] 서브넷이 다르면 Network ACL도 확인
- [ ] SSE를 쓴다면 `curl -N`으로 버퍼링 확인

**시연·오픈 전**

- [ ] 방화벽 규칙이 정기 점검에서 삭제되지 않도록 예외 등록
- [ ] 검증 기간 중 버전·설정 동결
- [ ] 자원 사용 추이 기록 (증설 근거)
- [ ] 백업·복구 경로 확인
- [ ] 당일 지원 연락 체계
